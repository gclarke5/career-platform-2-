# Exercise 05: Investigate a DNS or TLS failure

## 1. Setting and prediction

**This is the supplied simulation, not my real system.** The hostnames, IP
addresses and outputs below (`site.lab.example`, `198.51.100.24`,
`current-app.up.railway.app`, `203.0.113.44`) come from the exercise. I did not
run these commands, and none of them are results from `gavinclarke.me`.

I used the simulation because my real cutover to Railway (2026-10-13) didn't
leave me a dated failed DNS or TLS check to compare against. The checks I ran
after the switch all passed, and I wasn't going to break the live domain to
create a failure.

**The failed check:** `dig site.lab.example A` followed by
`curl -Iv https://site.lab.example/`.

**What should happen:** `site.lab.example` has moved to a new Railway
deployment, and the Railway URL already serves the current page and database
content. So I expect:

- `dig` returns a CNAME to `current-app.up.railway.app`, which resolves to
  Railway's address.
- `curl` connects to that Railway address, gets a certificate issued for
  `site.lab.example` that verifies, and receives `HTTP/2 200`.

## 2. Failed check and evidence

**Command:** the two checks above, supplied by the exercise. I interpreted
them on 2026-10-13.

**Actual result (simulated, supplied by the exercise):**

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

The zone still contains the old Azure record,
`site.lab.example. 300 IN A 198.51.100.24`.

## 3. Diagnosis

**DNS to the destination:** the name resolves to an A record for
`198.51.100.24`, the old Azure VM, not to a CNAME for
`current-app.up.railway.app`. `curl` then connects to that same address, so the
request goes to the old server, not Railway.

**TLS to the certificate:** the server at `198.51.100.24` presents its own
certificate, `CN=old-vm.lab.example`. That name doesn't match
`site.lab.example`, so curl stops with error 60 before any HTTP request is
sent.

**Which fault came first:** DNS. The TLS error is a symptom of reaching the
wrong machine, not a broken certificate on Railway. The observation that
supports this is the connected address: `Connected to site.lab.example
(198.51.100.24)` matches the stale A record in the `dig` answer. If DNS had
been right and only TLS were broken, curl would have connected to Railway's
address and failed there.

**Proposed repair (written before I opened the follow-up):** in Cloudflare,
delete the `site` A record pointing to `198.51.100.24` and add a `site` CNAME
to `current-app.up.railway.app`, left DNS only so Railway terminates TLS
itself. The ownership TXT record is already verified, so once traffic reaches
Railway it can serve a certificate for `site.lab.example`. I would not "fix" it
by putting a `site.lab.example` certificate on the old VM or by running curl
with `-k`. Either one would hide the problem while traffic still went to the
old server.

**What's still uncertain:**

- Whether Railway has already issued the certificate for `site.lab.example`.
  The TXT record verified, but certificate issuance can lag behind DNS.
- Whether every resolver drops the old answer at once. The TTL is 300, so
  caches should expire within about five minutes, but a single `dig` only shows
  one resolver.
- Whether the custom hostname serves the database content. A `200` on a HEAD
  request only shows that the app answered. It doesn't show the page body.

## 4. Repair and repeated check

**I didn't run this check. I'm interpreting the follow-up output the exercise
supplied**, after a lab operator made one record change:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

**The record change:** the `site` A record for `198.51.100.24` was replaced by
a CNAME to `current-app.up.railway.app`, which resolves to `203.0.113.44`.

| Check | Before (simulated) | After (simulated) |
| --- | --- | --- |
| DNS answer | `A 198.51.100.24` (old Azure VM) | `CNAME current-app.up.railway.app` → `A 203.0.113.44` |
| Connected address | `198.51.100.24` | `203.0.113.44` |
| Certificate subject | `CN=old-vm.lab.example`, name mismatch | `CN=site.lab.example`, verify ok |
| HTTP result | none (curl error 60 before HTTP) | `HTTP/2 200` |

**Compared with my proposal:** this is the same change I proposed, and the
results support my diagnosis, so I don't need to revise it. Fixing DNS alone
also fixed TLS, because the new destination already had the right certificate.
That confirms the certificate error came from reaching the wrong server.

The output doesn't prove the page shows the current database content on the
custom hostname. `curl -I` only returns headers. I'd confirm it with
`curl -s https://site.lab.example/` and look for content I know is in the
database.

## 5. What you learned

A useful check to separate DNS from TLS or application problems is to skip DNS
entirely and send the request straight to the intended destination:

```text
curl -Iv --resolve site.lab.example:443:203.0.113.44 https://site.lab.example/
```

`--resolve` makes curl use Railway's address for `site.lab.example` while still
sending the right hostname for TLS (SNI) and HTTP. If that works while a normal
`curl` fails, the problem is DNS. If it also fails with a certificate error, the
problem is TLS on Railway, such as a certificate that hasn't been issued yet. If
the certificate verifies but the response is a 5xx or the wrong page, the
problem is in the application.

I also learned that the address on curl's `Connected to` line is the quickest
link between the two layers. It shows which server the DNS answer actually
sent me to before I start reading certificate errors.

If the failure had remained after the change, I would next check:

- `dig @1.1.1.1` and `dig @8.8.8.8` to see whether resolvers disagree while
  old cached answers expire.
- Railway's domain settings, to see whether the certificate for
  `site.lab.example` is still pending.
